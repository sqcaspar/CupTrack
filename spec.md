### Brew Management Endpoints

#### GET /api/v1/brews
**Description**: Retrieve user's brew records with pagination and filtering
**Authentication**: Bearer token required
**Rate Limit**: 100 requests per minute

**Query Parameters**:
- `page` (optional): Page number, default 1
- `limit` (optional): Records per page, default 20, max 100
- `method` (optional): Filter by brewing method
- `dateFrom` (optional): Filter brews from date (ISO 8601)
- `dateTo` (optional): Filter brews to date (ISO 8601)
- `favorites` (optional): Filter only favorites (true/false)
- `sortBy` (optional): Sort field (createdAt, quality, brewNumber)
- `sortOrder` (optional): Sort direction (asc, desc)

**Example Request**:
```
GET /api/v1/brews?page=1&limit=10&method=pour-over&sortBy=createdAt&sortOrder=desc
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**Success Response (200 OK)**:
```json
{
```

### Error Response Format

All API endpoints follow a consistent error response format:

**Standard Error Response Structure**:
```json
{
  "success": false,
  "error": "ERROR_CODE",
  "message": "Human-readable error description",
  "details": [
    // Optional array of detailed error information
  ],
  "timestamp": "2025-08-05T10:30:00Z",
  "requestId": "req-uuid-123"
}
```

**Common Error Codes**:
- `VALIDATION_ERROR`: Invalid input data
- `AUTHENTICATION_REQUIRED`: Missing or invalid authentication token
- `AUTHORIZATION_FAILED`: Insufficient permissions
- `NOT_FOUND`: Requested resource not found
- `RATE_LIMIT_EXCEEDED`: Too many requests
- `SERVER_ERROR`: Internal server error
- `SERVICE_UNAVAILABLE`: Service temporarily unavailable

**HTTP Status Code Mapping**:
- 200: Success
- 201: Created successfully
- 400: Bad request (validation errors)
- 401: Unauthorized (authentication required)
- 403: Forbidden (insufficient permissions)
- 404: Not found
- 409: Conflict (duplicate resource)
- 429: Too many requests (rate limit)
- 500: Internal server error
- 503: Service unavailable

### Rate Limiting & Pagination

**Rate Limiting**:
- Authentication endpoints: 5-10 requests/minute
- Data retrieval: 100 requests/minute
- Data creation/modification: 50 requests/minute
- Export endpoints: 5 requests/minute
- Headers included: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`

**Pagination**:
- Default page size: 20 records
- Maximum page size: 100 records
- Pagination metadata included in all list responses
- Cursor-based pagination for large datasets
5. Integration Architecture
Frontend/Backend Communication
•	Protocol: HTTPS REST API calls
•	Authentication: Supabase JWT tokens passed in Authorization headers
•	Error Handling: Automatic retry mechanism with exponential backoff
•	State Management: React Context API for global state, local state for components
Authentication Flow
1. User initiates login (Google/Apple/Email)
2. Frontend redirects to Supabase Auth
3. Supabase returns JWT token to frontend
4. Frontend stores token and includes in API calls to Railway
5. Railway validates token with Supabase
6. API response includes refreshed token if needed
Data Flow Architecture
User Action → Frontend Validation → API Call → Backend Validation → 
Database Operation → Response → Frontend Update → UI Refresh
Error Handling Strategy
•	Network Errors: Automatic retry up to 3 attempts
•	Validation Errors: Display field-specific error messages
•	Server Errors: Generic error message with error ID for support
•	Transaction Failures: Automatic rollback with user notification
